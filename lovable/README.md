# Dashboard для Lovable

Весь фронтенд дашборда, подготовленный к переносу в Lovable. Это не вырезанный
кусок и не новый проект — те же 30 страниц, которые работают сегодня, включая
все семь разделов из плана (Daily Report, Weekly Report, Monthly Review,
Trends, Гант, Проекты, IT request) и всё остальное.

Папка лежит внутри `dashbord`, чтобы её можно было посмотреть и принять.
Для Lovable нужен отдельный репозиторий, где это содержимое лежит **в корне**
— Lovable ищет `package.json` на верхнем уровне.

---

## Проверено

`npm run build` проходит. Страницы открыты в браузере и читают нынешний
бэкенд на Render — без единой настройки:

| Адрес | Что показывает |
|---|---|
| `/` | Дашборд: вкладки Daily, Weekly, Trends, AI Usage |
| `/team-gantt` | Доска: 49 задач, 9 инженеров, 29 строк бэклога, номера `IT-` |
| `/projects` | Проекты |

| `/review/2026/10` | Октябрьский обзор целиком |

| `/it-requests/home` | Front door заявок |
| `/engineer/1` | Профиль инженера |

## Что изменено против нынешнего фронта

Три вещи, все — чтобы проект работал в Lovable сразу и чтобы переезд базы
потом не превратился в переписывание.

**1. Адрес бэкенда решается в одном месте.** `src/api/client.js` экспортирует
`API_ORIGIN` с зашитым адресом Render. Раньше четыре страницы
(`MonthlyReviewLive`, `Releases`, `ImportDialog`, `aiRegistry/shared`) считали
адрес сами из `VITE_API_URL`, и без этой переменной `/monthly-review` отдавал
ошибку разбора JSON вместо страницы. Теперь они берут `API_ORIGIN`.
`VITE_API_URL` по-прежнему перекрывает значение — для локального бэкенда.

**2. Слой данных.** `src/data/` — две реализации одного набора функций:
нынешний FastAPI и Supabase. Гант уже ходит через него (`ganttApi.loadBoard()`
вместо `fetch`), переключение идёт переменной `VITE_DATA_SOURCE`. Остальные
страницы пока ходят через `api/client.js` — он и есть их общий шов, и каждая
переезжает на слой данных тогда, когда до неё дойдёт очередь на Supabase.

**3. Tailwind.** Настроен для кода, который будет писаться дальше.
Существующие страницы им не пользуются — они оформлены токенами `--ios-*` в
`src/index.css`. `tailwind.css` импортируется после `index.css`, чтобы его
preflight ничего не сбросил.

## Два этапа

**Этап 1 — переезжает фронт, база остаётся.** Страницы живут на Lovable и
ходят в нынешний FastAPI на Render. Он уже отдаёт `allow_origins=["*"]`, на
сервере не меняется ничего. Данные, интеграции и ночные синки работают как
работали. Старый дашборд продолжает работать параллельно — это и есть откат.

**Этап 2 — переезжает база.** Схема применяется в Supabase, данные
переносятся, `VITE_DATA_SOURCE` переключается. Начало положено:
`supabase/migrations/0001_gantt.sql` — таблицы доски и бэклога, единая
нумерация `IT-`, функции чтения, отдающие ту же форму ответа что FastAPI, и
перенос задачи с доски в бэклог. RLS включён: читать можно, писать напрямую
нельзя, только через функции.

Чего в схеме нет и почему — в шапке самого SQL-файла. Коротко: очередь правок
доски (`apply-changes`, девять типов изменений со ссылками на временные id
внутри одной пачки) и два синка во внешние системы. Это переносится
построчно и с проверкой, а не по памяти.

Порядок именно такой, потому что менять хостинг и базу одним шагом нельзя:
при любой проблеме будет непонятно, где она, и откатываться будет некуда.

## Подключение к Lovable

1. Завести пустой приватный репозиторий — например `maico15/dashbord-lovable`.
2. Перенести туда **содержимое** этой папки, чтобы `package.json`, `index.html`
   и `src/` оказались в корне репозитория.
3. В Lovable: Import from GitHub → выбрать этот репозиторий.
4. Настраивать ничего не нужно — адрес бэкенда зашит в коде.

Дальше правки идут обычным пушем в этот репозиторий, Lovable подхватывает.

## Локально

```bash
npm install
npm run dev          # http://localhost:8080, данные с Render
VITE_API_URL=http://localhost:8000 npm run dev   # со своим бэкендом
```
